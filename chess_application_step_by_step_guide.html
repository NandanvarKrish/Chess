1. What are you building?

The target is a native desktop chess application that supports local two-player games, human-vs-computer games, legal chess rules, time controls, saved games, and analysis. The chess-playing logic must be your own C implementation—not a wrapper around Stockfish.

ApplicationMenus, board, interaction, clocks, history, themes, replay and statistics.
Chess enginePosition representation, legal move generation, evaluation, search and best-move output.
IntegrationA well-defined interface between Python and the C engine.
QualityPerft, unit tests, regression tests, profiling, packaging and documentation.
Core principle: correctness before strength, and strength before optimization. A fast engine that generates illegal moves is not a good engine.

2. Recommended architecture

Keep the application and engine separate. Python owns the user experience; C owns chess position state and chess rules. Both the Python bridge and UCI executable should use the same C engine core.

Python application + Pygame
Rendering · input · menus · clock · history · settings
↕
Communication boundary
ctypes shared-library API for board operations · UCI subprocess for search
↕
Custom C chess engine
Board · move generation · legal rules · make/unmake · evaluation · search
Supporting tools
CMake · Clang · CTest · pytest · LLDB · Git · SQLite

Why two communication methods?

  • ctypes: lets Python call a small, stable C API for loading positions, listing legal moves, applying moves and reading game state.
  • UCI: a standard text protocol for longer-running engine searches, time limits, depth, best moves, evaluation and principal variations.
Do not write two engines. The shared library and UCI executable must link to the same C source modules and rules implementation.

5. Build the C foundation before chess logic

Do not begin with a giant main.c. Create a tiny executable, learn the build cycle, then split the engine into modules.

First CMake project

Create engine/src/main.c:

#include <stdio.h>

int main(void) {
    puts("Chess engine foundation is running.");
    return 0;
}

Create engine/CMakeLists.txt:

cmake_minimum_required(VERSION 3.20)
project(chess_engine C)

set(CMAKE_C_STANDARD 17)
set(CMAKE_C_STANDARD_REQUIRED ON)
set(CMAKE_C_EXTENSIONS OFF)

add_executable(chess_engine src/main.c)

if(CMAKE_C_COMPILER_ID MATCHES "Clang|GNU")
    target_compile_options(chess_engine PRIVATE
        -Wall -Wextra -Wpedantic
    )
endif()

Build and run:

cmake -S engine -B build
cmake --build build
./build/chess_engine

Learn these C topics as you go

  • Headers, source files, declarations and definitions.
  • Structs, enums, pointers, arrays and integer types.
  • Stack versus heap, allocation and ownership.
  • Const correctness, error handling and API boundaries.
  • Compiler warnings, debugger use and sanitizers.
Use explicit board/state parameters in engine functions. Avoid global mutable board state; it makes testing, multiple games and search harder.

6. Represent the chessboard and parse FEN

Implement a simple, easy-to-debug board representation first. A 64-square array or 0x88 mailbox is suitable for the initial rules engine. After it is correct, add a bitboard representation and compare both implementations.

Conceptual board state

typedef struct {
    int squares[64];
    int side_to_move;
    int castling_rights;
    int en_passant_square;
    int halfmove_clock;
    int fullmove_number;
} Board;

This is an illustrative starter structure, not the final optimized representation. Choose a consistent piece encoding and document square indexing.

Implement in this order

  1. Map algebraic squares (a1 through h8) to array indices and back.
  2. Initialize the standard starting position.
  3. Print the board in a readable terminal format.
  4. Store side to move, castling rights, en-passant square and move counters.
  5. Parse FEN into a position, rejecting malformed input.
  6. Serialize the board back to FEN and test round trips.
A good test: load the starting FEN, serialize it, parse the result again, and verify every field matches.

7. Implement all legal chess rules

Generate pseudo-legal moves, then filter out moves that leave your own king in check. Keep move generation, attack detection and make/unmake responsibilities clearly separated.

OrderWorkImportant cases
1Move representationFrom, to, promotion and special-move flags
2Pawn movesSingle/double push, capture, promotion, en passant
3Knight movesBoard edges and occupied destinations
4Bishop, rook, queenSliding rays, blockers and captures
5King and attacksCheck, attacked squares and king adjacency
6CastlingRights, rook presence, empty path and attacked transit squares
7Legal move filteringPins and moves that expose the king
8Make/unmakeRestore every changed field exactly
9Game statusCheckmate, stalemate and draw conditions

Design make/unmake carefully

Before applying a move, save the captured piece, castling rights, en-passant square, halfmove/fullmove counters and hash key in an undo record. Unmaking must restore the exact prior position—not merely move the pieces back.

Implement repetition tracking and draw claims correctly. Distinguish automatic draws from claimable draws; include the 50-move/75-move rules and repetition rules required by the ruleset you adopt.

8. Prove the rules engine is correct

Perft recursively counts the legal positions reachable in a given number of plies. It is one of the most useful tools for finding move-generation bugs.

Starting position perft depthExpected nodes
120
2400
38,902
4197,281
54,865,609

When a count differs, implement divide output: show the node count for each legal root move. This narrows down the branch containing the bug.

Do not start serious search-engine work until legal move generation and perft are trustworthy.

9. Build the Pygame desktop interface

Build the interface against a temporary Python test controller first. This lets you work on rendering and interaction before the C engine is ready. Replace the temporary controller with the C bridge later.

  1. Initialize a Pygame window, event loop and frame clock.
  2. Draw an 8×8 board with correct light/dark square orientation.
  3. Load piece artwork and scale it cleanly for each square.
  4. Map mouse coordinates to board squares.
  5. Support selection, legal-destination highlights and move input.
  6. Add captured pieces, move list, last-move highlight and check indicator.
  7. Add undo, redo, restart, board flip and promotion choice.
  8. Add menus, settings, themes, sound and accessibility options.

10. Connect Python to the C engine

Part A — Shared library API

Expose a small C interface with opaque or carefully documented handles. Start with functions to create/destroy a game state, load FEN, get legal moves, apply a move, query status and export FEN. Define ownership and buffer sizes explicitly.

Compile a shared library for macOS (typically a .dylib) using CMake. In Python, load it with ctypes.CDLL and declare argtypes and restype for every function. Never assume C and Python structure layouts match unless you deliberately define and test the ABI.

Part B — UCI engine process

Run the standalone C engine as a subprocess for searches. Implement the essential commands:

uci
isready
ucinewgame
position startpos
position fen <FEN>
go depth 8
stop
quit

The engine should answer with protocol messages such as uciok, readyok, info and bestmove. Parse output without freezing the Pygame event loop. Use a worker thread or asynchronous process reader for search.

One C engine core, two front doors: a shared-library API for direct game operations and UCI for search. Keep the rules and search implementation in C.

11. Build the first playable AI

Start with a basic but correct search, then add strength improvements incrementally. Use a fixed test suite so you can tell whether a change actually helps.

  1. Evaluation: material values and a score from the side-to-move perspective.
  2. Minimax: understand the game tree and maximizing/minimizing turns.
  3. Negamax: simplify the zero-sum search implementation.
  4. Alpha-beta: prune branches that cannot improve the current result.
  5. Iterative deepening: search depth 1, then 2, then 3, retaining the last completed result.
  6. Time management: stop safely when the allotted time is reached.

Report depth, node count, elapsed time, nodes per second, score and principal variation. The UI should remain responsive while the engine thinks.

Search safety

  • Always have a legal fallback move when a search is interrupted before completing a deeper iteration.
  • Handle checkmate scores consistently, including distance-to-mate preferences.
  • Test terminal positions and zero-legal-move positions.
  • Make sure cancellation and process shutdown do not corrupt state.

12. Improve engine strength and speed

Add one feature at a time, measure it, and retain it only when correctness and performance tests remain sound.

FeatureWhat it contributes
Piece-square tablesRewards useful piece placement.
Pawn structureRecognizes doubled, isolated and passed pawns.
MobilityMeasures available piece activity.
King safetyEstimates exposure and defensive cover.
Move orderingFinds promising moves earlier, improving pruning.
Quiescence searchReduces unstable evaluations at tactical leaf positions.
Killer/history heuristicsImproves ordering using prior search information.
Zobrist hashing + transposition tableIdentifies repeated positions and reuses search results.

Move from a simple array/mailbox representation to bitboards only when you can validate both against the same test positions and perft results. Optimization is a measured engineering task, not a visual rewrite.

14. Test, profile and release

Testing layers

  1. C unit tests: board, FEN, attacks, moves, make/unmake, evaluation and search.
  2. Perft tests: known positions and expected node counts.
  3. Python tests: controllers, clocks, PGN handling and settings.
  4. Integration tests: shared library, UCI protocol, process interruption and synchronization.
  5. Strength/performance tests: tactical positions, self-play, nodes per second, memory and time controls.

Debug build with sanitizers

clang -g -O1 \
  -fsanitize=address,undefined \
  -fno-omit-frame-pointer \
  your_test_sources.c -o chess_debug

Prefer a CMake debug configuration for the real multi-file project. Use LLDB for stepping and stack traces; use Instruments when you need to profile the macOS application. Run release benchmarks separately from sanitizer builds.

16. Free learning and reference resources

Use documentation and reference implementations to understand standards and test correctness. Do not copy another engine and present it as your own.

  • Chess Programming Wiki — board representations, move generation, evaluation and search.
  • Pygame documentation — events, surfaces, drawing, fonts and timing.
  • CMake documentation — targets, libraries and build configurations.
  • Python documentation — language and standard library.
  • python-chess documentation — optional reference for chess rules, PGN/FEN and test comparisons.
  • Stockfish source — optional advanced benchmark/reference; not your engine implementation.
  • UCI protocol overview — engine communication protocol.
  • AddressSanitizer documentation — memory error detection.

Your first development sprint

Do not try to build all 75 modules at once. Your first sprint is deliberately small: make a reliable C project that builds, tests and can be debugged.

Definition of done: A fresh clone can be configured, compiled and tested using documented commands. Then move to board representation and FEN.
Build incrementally. Verify every rule. Measure every optimization. Make the engine yours.
